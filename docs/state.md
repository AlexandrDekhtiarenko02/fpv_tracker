Этот файл — точка входа. Если контекст переписки потерян, читать первым.

| | |

## Как снять образец и посмотреть, что решал трекер

**На малине** — снять кадры:

```bash
cd ~/fpv_tracker && ./record.sh on      # включит и перезапустит службу
# захватить цель, поводить; запись идёт, пока идёт слежение, предел 25 с
./record.sh off                          # ОБЯЗАТЕЛЬНО выключить
```

**На Mac** — забрать и разобрать:

```bash
cd ~/Desktop/fpv_tracker
./fetch_logs.sh                          # заберёт логи и записи
python3 tools/render.py                  # разберёт ВСЕ записи
```

В `flight_logs/rendered/<запись>/` появится:

| | |
|---|---|
| `<запись>.mp4` | видео с рамкой, прицелом, размером и совпадением на каждом кадре. **Красная рамка = рамка стоит на фоне, а не на цели** |
| `разбор.csv` | то же числами, покадрово |
| `итог.txt` | сводка: сколько кадров велась цель, среднее совпадение, рост коробки, доля кадров на фоне |

Прогон идёт через НАСТОЯЩИЙ `tracker.py`, а не через упрощённую копию:
проверено, расхождение с бортовым решением 0.0 px.

Ещё два средства:

```bash
python3 tools/sweep.py                        # все записи одной таблицей
python3 tools/sweep.py --set DIST_PENALTY=0.3 # подбор настройки перебором
```

**Почистить логи, сохранив записи:**

```bash
./clean_logs.sh          # покажет, что удалит
./clean_logs.sh --yes    # удалит логи, записи и разборы ОСТАВИТ
```

## Запись кадров — как сравнивать честно

Сравнивать прогоны между собой НЕЛЬЗЯ: разные цели, разный фон, разная манера
водить. На этом уже зарезана хорошая ветка (`search-window`) и едва не принята
плохая.

Правильный путь — запись сырых кадров и разбор на земле:

```bash
# на малине: включить RECORD_FRAMES = True, перезапустить, снять образец
cd ~/fpv_tracker && ./fetch_logs.sh          # с Mac, запись приедет вместе с логами
python3 tools/replay.py flight_logs/recordings/<метка>
```

По записи любой вариант алгоритма прогоняется по ОДНИМ И ТЕМ ЖЕ кадрам,
сколько угодно раз. Только так спор «переписывать или добивать» решается
замером, а не мнением.

Запись 320x240 без сжатия: 75 КБ на кадр, около 1.9 МБ/с, пределы 25 с и
120 МБ. В камерном потоке только копия и очередь, диск — в отдельном потоке.

## Правило веток — нарушать нельзя

**В `main` попадает только то, что проверено на борту и работает.** Любая
непроверенная правка живёт в своей ветке по теме (`color-*`, `size-*`,
`motion-*`) и вливается только после замера, подтвердившего пользу.

Я это правило уже нарушил один раз: положил цветовой маяк прямо в `main`
до всякой проверки. Пришлось откатывать. `main` — это то, что оператор
может залить на борт не глядя; непроверенный код там ломает единственную
опору, на которую можно встать при откате.

## Ветки

| Ветка | Что содержит | Состояние |
|---|---|---|
| `main` | всё принятое и проверенное на борту, включая оба исправленных знака и наклон камеры | проверено на стенде |
| `color-beacon` | `main` + возврат рамки по цвету | **сломана**: после прыжка шаблон не пересобирается, а обновляется он только при score >= 0.60, которого после прыжка не бывает |

Веток всего две — так и должно быть. Отвергнутые опыты веток не занимают,
но код никуда не делся: он помечен метками `otvergnuto/psr-radius`,
`otvergnuto/match-weight`, `otvergnuto/exposure`, `otvergnuto/search-window`.
Вернуться к любому: `git checkout otvergnuto/search-window`. Числа, по
которым их отвергли, — в `experiments.md`.

Полный список меток: `git tag -l 'otvergnuto/*'`.

**Удаление ветки на GitHub не убирает её с малины.** У малины свой клон: в
нём остаются и локальные копии веток, и следы `origin/*`. Чистить надо
отдельно, обычный `git pull` этого не делает:

```bash
cd ~/fpv_tracker && git fetch --prune origin && git branch -D <ветки>
```

Проверить, что чистить безопасно (код есть в `main` или под меткой):

```bash
git merge-base --is-ancestor <ветка> origin/main && echo "в main"
git rev-parse -q --verify otvergnuto/<ветка> && echo "под меткой"
```

**Барометр — закрыто.** Датчик исправен, источник один, читаем правильный.
Единственное условие — арм: без него оценщик высоты в Betaflight не работает
(вариометр ровно 0). Дальность в метрах ждёт только первого полёта.

**Открыто, замерено, не починено:** компенсация тангажа упирается в предел
`MAX_PITCH_COMP_PX = 100`. При 11.7 px/° это насыщение уже на **8.55°**, и на
стенде она стояла на упоре в **48% кадров**. В пикировании на 20-30° будет на
упоре постоянно. Чинить отдельной правкой: поднять число мало, надо понять,
чем оно обосновано — при цели у горизонта компенсация физически доходит до
полукадра.

**Следующая одиночная правка:** починить маяк в `color-beacon`. Он доказал,
что ставит рамку на цель (`color_best` падал 1.00 -> 0.12), но после прыжка
шаблон остаётся старым, а обновляется он только при score >= 0.60 — которого
после прыжка не бывает. Нужно пересобирать шаблон сразу после возврата.

## Что проверено в воздухе, а что нет

**Проверено на стенде оператором:** всё по трекингу (см. `experiments.md`).

**НЕ ПРОВЕРЕНО В ПОЛЁТЕ вообще:** весь контур управления — разгон по углу,
устранение ратчета газа, привязка ко времени, оценка сближения, высотомер.
Проверялось только на моделях и стендом. Первый реальный вылет с этим кодом
ещё предстоит.

## Как понять, что летит

```bash
cd ~/fpv_tracker && ./status.sh
```
Сверяет md5 запущенного процесса с файлом на диске. `git pull` меняет файл, но
служба продолжает выполнять код, загруженный в память при старте — перезапуск
обязателен.

## Обновить код на малине

```bash
cd ~/fpv_tracker && git pull && sudo systemctl restart tracker && sleep 6 && ./status.sh
```
