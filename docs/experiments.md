# Журнал опытов по трекингу

Каждая строка — один проверенный опыт на реальном борту. Смысл журнала в том,
чтобы **не повторять уже отвергнутые гипотезы** и не терять числа.

Правило работы, выведенное на собственных ошибках: **одна правка — один
замер**, предсказание формулируется ДО прогона и записывается в коммит.

## Методологические выводы

**Средний захват мерил не то.** Во всех версиях захваты заканчивались тем, что
оператор отпускал AUX: за все прогоны один уход в HOLD и ни одного LOST.
Метрика отражала ритм тестирования, а не качество. Выводы, сделанные по ней,
пришлось пересмотреть.

**Средний score тоже обманчив.** Он РАСТЁТ, когда трекер уверенно сидит на
неподвижном фоне: фон совпадает с шаблоном идеально. Высокий score не
означает, что рамка на цели.

**Что оказалось честнее:** расхождение матча с предсказанием потока
(`match_flow_gap`) и прямые наблюдения оператора.

**Доля провальных кадров тоже обманывает — и хуже всех.** Она считается
только внутри захвата. Если правка заставляет трекер БРОСАТЬ трудные цели,
эти кадры просто исчезают из знаменателя, и метрика улучшается именно там,
где стало хуже. На `search-window` она показала 23%% → 9%% при пяти реальных
потерях против нуля. **Всегда считать уходы в HOLD рядом с любой метрикой
качества.**

**Проверка на подмену условий.** Прежде чем верить сравнению, надо убедиться,
что оператор водил цель одинаково. Здесь проверено: быстрее всего цель
двигалась как раз в прогоне `main` (4.7 px/кадр, 42%% быстрее 5 px) — и там
ни одной потери. То есть потери на `search-window` не объясняются тем, что
в тех прогонах водили резче.

**Наблюдения оператора били все мои гипотезы.** «Быстрее ведёшь — быстрее
срывается», «объект меньше пятна на фоне — прыгает», «на крупном фактурном
фон перебивает» — каждое указывало на механизм точнее, чем мои рассуждения.

## Замена алгоритма слежения — проверено, пока не нужна

Вопрос оператора: не переписать ли трекер целиком. Замерено, что вообще
доступно на этом железе:

| | |
|---|---|
| KCF, CSRT, MOSSE | **вырезаны** из opencv-contrib 4.13 |
| TrackerMIL | есть, но **3949 мс на кадр** — четыре секунды |
| Nano / Vit / DaSiamRPN | нейросетевые, нужны файлы моделей, на Zero 2W безнадёжны |
| корреляционный фильтр своими руками | **та же цена**, что нынешний матч: 5.9 против 5.6 мс при окне 48, 13.0 против 12.2 при 96 |

Выигрыша в скорости нет. Разница только в природе: наш матч ПОРОЖДАЮЩИЙ
(«найди похожее на сохранённое»), корреляционный фильтр РАЗЛИЧАЮЩИЙ (обучается
отличать цель от окружения, фон входит как отрицательные примеры). Это ближе
к нашей болячке «цепляется за фон», но переписывание не починило бы ни одного
из дефектов, найденных за день: перевёрнутый знак, удвоение вместо гашения,
рассинхрон размера эталона, разомкнутая обратная связь, забытые потолки. Они
бы просто переехали в новый код.

Решение: не переписывать, пока не появится запись кадров, по которой варианты
можно сравнить честно.

## Открытые вопросы

**Коробка не определяет размер цели.** Стоит на значении по умолчанию (8 px в
координатах трекинга) в 76% кадров, максимум за заход 26 px. Для крупного
объекта трекер ведёт случайный участок его текстуры, неотличимый от участка
фактурного фона. Причина измеряется: в лог пишутся `size_est` и `size_skip`
(0 применена, 1 нет матча, 2 score ниже порога, 3 оценка вне диапазона).

**Рамка уползает к краю при сближении.** Шаблон застревает в старом масштабе.
Две попытки лечения были хуже болезни (см. отвергнутое). Остался непроверенный
третий вариант под флагом `TEMPLATE_RESCALE_ON_SIZE_CHANGE`: масштабировать
эталон, снятый при захвате, — он свободен от обеих найденных причин.

## Как воспроизвести замер

```bash
c=$(ls -t ~/fpv_tracker/flight_logs/*.csv | head -1)
grep -m1 -o "commit=[0-9a-f]*" ${c%.csv}.events.log
awk -F, 'NR>1 && $4=="TRACKED" {s+=$10;n++; if($10<0.4)b++} \
  END {printf "score=%.3f плохих=%d%% кадров=%d\n", s/n, 100*b/n, n}' $c
```

## Подбор по записям — первый раз не на глаз

Семь записей со стенда, 2600 кадров, `tools/sweep.py`. Мерило не зависит от
чьего-либо мнения: камера на стенде НЕПОДВИЖНА, значит движется только рука с
целью, и рамка на неподвижном пикселе — это рамка на фоне.

| `DIST_PENALTY` | рамка на фоне |
|---|---|
| 0.55 (было) | 6.1% |
| 0.42 | 3.2% |
| 0.30 | 3.1% |
| **0.20** | **2.6%** |
| 0.12 | 2.6% |

Главный выигрыш там, где оператор и жаловался, — запись `175812`, уход на
перфорированную стену: **17.5% → 1.7%**. Запись `175748`: 6.7% → 0.0%.

Механизм не случаен: предсказание потока САМО сползает на фон, а сильный штраф
заставлял совпадение держаться возле сползшего предсказания.

**Что НЕ помогло** (проверено, чтобы не пробовать снова):

| попытка | итог |
|---|---|
| `MOTION_PENALTY` 0.5 → 0.9 и 1.2 | без изменений |
| `MOTION_REF_DIST` 3.0 → 0.5 | без изменений |
| `MOTION_DIFF_REF` 4.0 → 1.5 | без изменений |
| `MOTION_MIN_SEPARATION` 1.5 → 0.3 | 6.1% → 3.8% **сама по себе**, но с `DIST_PENALTY` 0.20 не складывается |
| `MATCH_WEIGHT` 0.22 → 0.5 | 3.0% — хуже, чем один `DIST_PENALTY` |
| `DIST_PENALTY` вверх (0.75, 0.95) | 6.2% и 11.6% — **резко хуже** |

Защита по движению почти не срабатывала: различимость движения 0.55 при пороге
1.5, то есть цель двигалась медленнее порога.

**Остался нерешённым случай `175804` — 37%.** Рамка уходит на стену к 38-му
кадру и там остаётся. По кадрам видно: цель мелкая и малоконтрастная, а
перфорированная стена — правильный повторяющийся узор. Это тот самый предел
порождающего матча: он ищет похожее, а не отличное от фона.

**Оговорка.** Все семь записей сняты неподвижной камерой при медленном
движении. В полёте камера движется сама, и предсказание потока значит больше.
`DIST_PENALTY` проверять на первом живом заходе.

## Цвет отвергнут по прямому сравнению

Пятнадцать записей С ЦВЕТНОСТЬЮ, один и тот же код прогнан с цветом и без.

| | рамка на фоне |
|---|---|
| с цветом | **18.6%** |
| без цвета | **17.5%** |

По записям цвет **ни разу не помог**, а трижды навредил:

| запись | с цветом | без цвета |
|---|---|---|
| 131038 | 20.1% | **14.5%** |
| 131204 | 80.6% | **75.0%** |
| 131212 | 26.1% | **17.8%** |

В девяти записях разницы ровно ноль, в трёх хуже, ни в одной лучше. Эффект
односторонний — это не шум.

**Почему.** Цветность вдвое грубее яркости и сильно размыта, а цели у нас
мелкие, десятки пикселей. Карта штрафа выходит грубее самой цели и сдвигает
пик, вместо того чтобы его уточнять. Различимость при этом меряется ВЕРНО:
там, где она высокая (88.4), цвет и вредил сильнее всего.

**Важно для истории.** Прежнее впечатление «с цветом трекер лучше держится»
было снято на глаз, на другой сборке и до полутора десятков других
исправлений. Прямое сравнение на одних и тех же кадрах его не подтверждает.
Это второй за два дня случай, когда впечатление разошлось с замером.

**Что с камерой.** Отдельный вопрос закрыт: камера цвет отдаёт нормально —
на кадрах видны синяя коробка, оранжевые детали, тон кожи. Обесцвеченными
были не кадры, а сами цели: тёмно-серые предметы на сером стенде.

## Стенд исчерпан: его худший случай в полёте не встречается

Пятнадцать записей с цветом дали неожиданную связь: **чем МЕДЛЕННЕЕ двигалась
цель, тем ХУЖЕ результат**. Связь −0.56.

| запись | рамка на фоне | скорость цели |
|---|---|---|
| 131204 | **75.0%** | **0.1 px/кадр** |
| 131016 | **66.1%** | **0.3 px/кадр** |
| 131121 | 6.0% | 1.1 px/кадр |
| 131049 | 9.3% | 1.1 px/кадр |

Причина понятна: на стенде камера НЕПОДВИЖНА. Когда цель тоже почти стоит,
относительного движения нет вовсе — и у трекера не остаётся ни одного признака,
кроме внешнего вида. Рамка сползает по пикселю на перфорированную стену, и
вернуть её нечем.

**Но в полёте этого случая не будет.** Там цель почти неподвижна в кадре — мы
летим В НЕЁ, — зато ФОН ПРОНОСИТСЯ мимо. Считано при 25 м/с для точки фона в
30 м вбок от линии визирования:

| дальность цели | движение фона |
|---|---|
| 200 м | 0.3 px/кадр |
| 100 м | 0.9 px/кадр |
| 60 м | 2.3 px/кадр |
| 40 м | **4.1 px/кадр** |

Признак сильнее стендового в 5-15 раз и **растёт по мере сближения** — то есть
крепнет там, где важнее.

**Вывод.** Дальнейшая подгонка по стендовым записям опасна: мы будем чинить
случай, которого в работе не бывает, и рискуем сломать тот, который бывает.
Это ровно ловушка `DIST_PENALTY`, только теперь видно ЗАРАНЕЕ.

Стенд свою работу сделал: на нём найдены и устранены рассинхрон размера
эталона, разомкнутая обратная связь по масштабу, безликий эталон, три потолка
и переподгонка. Дальше нужны записи ИЗ ПОЛЁТА.

## Цвет вернулся — но как КАРТИНКА для поиска, а не как штраф

Отсев по цвету штрафом был отвергнут замером (см. выше). Но провалился
**способ, а не признак**. На тех же 15 записях с цветностью:

| контраст цель/фон | по яркости | по цвету |
|---|---|---|
| 131204 (75% срывов) | 5.4 | **110.0** |
| 131140 | 0.9 | **63.7** |
| 131121 | 0.7 | **22.3** |
| 131116 | 1.6 | **30.6** |

Ровно там, где трекер срывался, цель по яркости почти невидима, а по цвету
видна прекрасно.

**Правильный способ.** Не штрафовать поверх поиска по яркости, а строить
картинку, в которой цветовое отличие превращено в яркостное, и искать по ней
обычным образом. Берётся направление «цель минус фон» в цветности, снятое при
захвате, и каждый пиксель проецируется на него.

Оранжевое на сером становится ярким. **А фактура фона схлопывается** — она
отличается яркостью, а не цветом. Перфорированная стена, на которую срывался
трекер, в этой картинке просто пропадает.

**Результат по 15 записям:**

| | рамка на фоне |
|---|---|
| было (яркость) | 17.5% |
| **стало** | **5.8%** |

По записям: из восьми заходов, где выбран цвет, **семь дали ровно 0.0%**.
Все оставшиеся провалы — там, где цвет не выбрался.

**Что оказалось важным по дороге:**

* **Ось цвета принадлежит захвату.** Пока она жила после потери лока, новая
  цель искалась по проекции, снятой со старой, а следующая ось снималась с уже
  спроецированной картинки. Обе ошибки тихие. Сброс дал 19.1% → 9.5%.
* **Порог перехода 0.5, а не 1.4.** Переходить стоит даже когда цвет выигрывает
  у яркости вдвое меньше единицы: проекция не просто добавляет контраст цели,
  она ещё и УБИРАЕТ фактуру фона. 9.5% → 5.8%.

**Цена:** 5.9 мс на кадр при бюджете 38. Платится только когда цвет выбран.

**Оговорка.** Замерено на стенде. Направление оси снимается при захвате; если в
полёте освещение заметно поменяется по ходу захода, ось поплывёт. Проверять на
первых же лётных записях.

## Бесплатная оптимизация: цвет стал ДЕШЕВЛЕ яркости

Оператор: «трекер цепляется как мёртвый, но просел ФПС». Профилирование
показало, куда уходит кадр, — и что дорого было совсем не то, что казалось.

**1. Цветовая проекция: 5.85 → 0.54 мс.** Считалась в дробных числах по
БОЛЬШОЙ картинке. Достаточно раскрыть скобки и посчитать одним действием на
МАЛОЙ — цветность вчетверо меньше кадра:

    128 + ((U-ou)*du + (V-ov)*dv)*k  =  U*(du*k) + V*(dv*k) + const

Результат слежения не изменился: 5.8% против 5.9%.

**2. Поток оказался САМЫМ дорогим узлом** — 8.1 мс против 4.0 у самого
совпадения. Причина: оконный расчёт был включён только для 640×480, а на нашем
разрешении поток считался по ПОЛНОМУ кадру каждый кадр.

Рассуждение в комментарии было верным для тогдашнего запаса: при постоянных 72
окно занимало почти весь кадр. Теперь запас считается от самих точек и выходит
около 45 — окно примерно 114×114 против кадра 320×240, вшестеро меньше площади.

Плюс подобрано перебором по 39 записям: уровней пирамиды 2→1, итераций 14→8.
Результат не изменился ни на одном варианте — поток был настроен на движения
в десятки пикселей, которых у нас не бывает.

**Тест поймал регрессию по дороге.** Попытка просто уменьшить запас до 40
разошлась с полнокадровым потоком на 5 px: точки крупной цели вылезали за край
окна. Отсюда и переменный запас вместо числа.
