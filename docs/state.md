## Что это

Донаведение для FPV-аппарата: трекер захватывает цель по указанию оператора и
доводит машину до неё на последнем участке, где связь ненадёжна. Две части —
**слежение** (удержать цель в кадре) и **управление** (превратить положение
цели в команды на полётник через MSP OVERRIDE).

Железо: Raspberry Pi Zero 2W, камера IMX219, полётник GEPRC F405 с
Betaflight. Обработка 320×240, бюджет кадра 38 мс.

## Правила, выведенные на своих ошибках

1. **Измерять, а не предполагать.** Каждое утверждение — с числом. Каждая
   правка — с замером до и после.
2. **В `main` только проверенное.** Непроверенное живёт в своей ветке.
3. **Подбор проверять на данных, которых он не видел.** Настройка
   `DIST_PENALTY` была подобрана на 7 записях, улучшила вдвое — и на 17 новых
   ВРЕДИЛА. Откачена.
4. **Считать уходы в HOLD рядом с любой метрикой качества.** Доля провальных
   кадров считается только внутри захвата: если правка заставляет трекер
   БРОСАТЬ трудные цели, метрика улучшается там, где стало хуже. Так была
   зарезана ветка `search-window`.
5. **Впечатление оператора важнее моих метрик.** Дважды его наблюдение
   оказывалось верным против моих чисел, и дважды числа мерили не то.
6. **Сравнивать прогоны между собой нельзя** — разные цели, фон, манера. Для
   сравнения есть записи (ниже).

## Приборы — главное, что стоит освоить сразу

```bash
python3 tools/sweep.py                  # прогнать НАСТОЯЩИЙ трекер по ВСЕМ записям
python3 tools/sweep.py --set ИМЯ=знач   # подбор перебором
python3 tools/sweep.py --only 20260902  # только часть записей
python3 tools/offline.py <запись>       # одна запись подробно
python3 tools/render.py                 # разбор всех записей в видео с рамками
python3 tools/check_names.py tracker.py # имена, использованные но не заданные
./run_tests.sh                          # все проверки, работает и на малине
```

`tools/offline.py` подсовывает заглушки железа и гоняет **сам `tracker.py`** —
проверено, расхождение с бортовым решением 0.0 px. То есть любую правку можно
проверить на записях без вылета.

**Мерило качества:** доля кадров, где рамка стоит на НЕПОДВИЖНЫХ пикселях.
Камера на стенде неподвижна, значит движется только цель — рамка на
неподвижном пикселе это рамка на фоне. От мнения не зависит.

Записи: `flight_logs/recordings/`, 39 штук, 15 из них с цветностью.
**Это испытательный набор, удалять нельзя.** `./clean_logs.sh` их сохраняет.

## Съёмка образцов

На малине: `./record.sh on` (или `hi` — двойное разрешение в файл), потом
обязательно `./record.sh off`. С Mac: `./fetch_logs.sh`.

Настройки борта — в `local_settings.py` (не в репозитории, обновлением не
затирается). `record.sh` меняет там только параметры записи, сохраняет
координаты и прочие настройки, а при `on`/`hi` сам включает `OBSERVE_ONLY`.

## СЛЕЖЕНИЕ: состояние

Итог по 15 записям с цветностью: **5.8–6.3% кадров на фоне, 56 кадров/с.**
Оператор: «трекер цепляется как мёртвый».

Что сделано и подтверждено замером (подробности — `docs/experiments.md`):

| | |
|---|---|
| **Слежение по цвету** | вместо яркости строится картинка «близость к цвету цели». Фактура фона схлопывается. 17.5% → 5.8% |
| Замкнут контур масштаба | коробка догоняет цель и ОСТАНАВЛИВАЕТСЯ |
| Рассинхрон размера эталона | уводил рамку систематически, в одну сторону |
| Три потолка размера | один из них поставил я сам |
| Безликий эталон | внутри однородной цели эталон терял все признаки |
| Размер при захвате | брался по умолчанию, а не измерялся |
| Оптимизации | проекция вдесятеро, оконный поток на 320×240. 49 → 56 кадров/с |

**Отвергнуто замером, не повторять:** цвет как ШТРАФ (не помогал ни разу,
трижды вредил); `search-window`; `psr-radius`; `match-weight`; `exposure`;
`TEMPLATE_SCALE=1.3`. Все под метками `otvergnuto/*`.

### Пределы слежения

* **Дальность.** На 320×240 машина 4 м даёт 13 px на 100 м. Дальше вести
  нечего. Это разрешение, а не алгоритм. Цена двойного: узлы 9.2 → 24.8 мс при
  бюджете 38. Режим `./record.sh hi` сделан, чтобы проверить на записях —
  **данных пока нет**.
* **Показатель годности захвата НЕ ПОЛУЧИЛСЯ.** Три признака дали точность
  около 55% — половина предупреждений ложные. Ставить не стал.
* **Стенд исчерпан.** Его худший случай — медленная цель при НЕПОДВИЖНОЙ
  камере — в полёте не встречается: там фон проносится мимо, и признак
  движения сильнее в 5–15 раз. Дальнейшая подгонка по стенду опасна.

## УПРАВЛЕНИЕ: состояние

**Ничего не проверено в полёте.** Всё измерено на стенде.

Найдено и исправлено (подробности — `docs/control-loop.md`):

| дефект | последствие |
|---|---|
| Компенсация тангажа СКЛАДЫВАЛАСЬ с ошибкой | прицельная ошибка удваивалась. −17.4 → −5.5 px/° |
| Угол снижения считался зеркально | дальность указывала бы НАЗАД |
| Наклон камеры 6.9° не учитывался | дальность занижалась вдвое на дальней цели |

**Знак тангажа установлен замером:** рост тангажа от FC = НОС ВНИЗ. Цель
смещается −12.2 px на градус (связь −0.92), картинка не перевёрнута.

### Главная слабость управления

**Ключевые числа выдуманы.** `AIM_OFFSET_Y = 10`, `LEAD_FRAMES = 4`,
`P_GAIN_*`, `D_GAIN_*`, `FF_GAIN_*` — поставлены на глаз и никогда не
проверялись в воздухе. Это не «плохо настроено», а «настройки нет».

### Открытое, замерено но не починено

* **Предел компенсации** `MAX_PITCH_COMP_PX = 100` — насыщение уже на 8.55°,
  на стенде стояла на упоре 48% кадров. В пикировании будет постоянно.
* **Газ не знает ни дальности, ни времени до цели.** Управляется ТОЛЬКО
  положением цели в кадре по вертикали. Две беды:
  - нет упреждения по наклону: при 30° нужно на 15% больше тяги, и это
    известно заранее по тангажу, а газ узнаёт только когда цель просядет;
  - газ считается по СЫРОМУ `dy_alt`, без поправки на наклон, — то есть
    разгон сам себе подкручивает газ. Очищенный вариант `dy_alt_decoupled`
    пишется в лог, но в управление не подан.
* **Нет торможения к цели.** Скорость доворота аппарата равна `a/v`, а
  требуемая растёт как `1/R²`. Запас падает как **квадрат скорости**. Граница,
  за которой доворачивать нечем, приходится на **0.9 с до цели при любой
  скорости** — значит закон торможения писать по `tau`, а не по дальности.
* **Режим сближения** переключается по `box_frac >= 0.18`, что зависит от
  размера цели. Правильнее по `tau`.
* Каскадный газ по вариометру написан, но выключен.

## ЧТО ДЕЛАТЬ ДАЛЬШЕ

Ветка **`pilot-demo`** — сбор данных по вылетам. Подробности:
`docs/sbor-dannyh.md` и `docs/pilot-demo.md`.

Замысел: трекер СМОТРИТ И ПИШЕТ, заходы выполняет пилот руками. Из его
действий выводится закон наведения.

### Что уже сделано в ветке

* **`OBSERVE_ONLY`** — оверрайд не включается и `MSP_SET_RAW_RC` вообще не
  отправляется. Иначе даже passthrough считается свежим MSP override: при
  поднятом AUX4 Betaflight подменяет приёмник кэшированными значениями, и
  пилот теряет управление. Закреплено тестом.
* **Папка на каждый захват** `flight_logs/zahvaty/<метка>_zahvatNN/` со
  строками, событиями и итогом. В итоге написано, ЧТО БЫЛО ДОСТУПНО.
* **Гироскоп** (MSP_RAW_IMU) — в ACRO стик задаёт угловую СКОРОСТЬ, связь
  «стик → поведение» меряется по нему, а не по отфильтрованным углам.
* **GPS** (MSP_RAW_GPS) плюс `TARGET_LAT/LON` из настроек борта.
* **Путевая скорость по бегу земли** — замена GPS.

### ГЛАВНОЕ ОГРАНИЧЕНИЕ КАМПАНИИ

**GPS будет только на время замеров. На серийном борту его нет.** Значит закон
не имеет права зависеть ни от одной величины из GPS. Закреплено списками
`PRODUCTION_COLUMNS` / `CAMPAIGN_ONLY_COLUMNS` и тестом.

Роль GPS — **опорная величина в подгонке**, а не проверка после. Правильный
порядок (проверено на модели):

1. по GPS находится ПОПРАВКА к бортовой оценке дальности и скорости;
2. поправка остаётся в коде и работает без GPS;
3. закон подгоняется уже по исправленной величине.

Подгонка сразу по GPS-величинам — ловушка: закон выйдет верным и в поле будет
врать вдвое, потому что на вход ему пойдёт другая величина.

Отсюда: **GPS должен стоять всю кампанию**, а не пару вылетов.

### Вид закона точки прицеливания

```
смещение = a·(скорость визирования) + b·(собственный тангаж) + c
                    ↑                        ↑                  ↑
              из кампании           УЖЕ ЕСТЬ: 11.7 px/°   из кампании
```

`b` — это компенсация тангажа, у которой сегодня исправлен знак. Из кампании
нужны, по сути, `a`, `c` и упреждение газа по наклону.

Угол снижения и время до цели входят не слагаемыми, а условиями: угол задаёт
раскладку по осям кадра, `tau` — момент переключения фазы и торможение.

### Как разложить вылеты — важнее их количества

* высоту и дистанцию менять свободно, GPS запишет фактические;
* **мешать высокое с близким и низкое с дальним** — иначе угол захода не
  изменится, и сотня вылетов даст ОДНУ точку;
* захватывать края диапазона;
* минимум три связки по пять заходов, лучше около сотни;
* **откладывать целые связки на проверку**, а не отдельные заходы.
