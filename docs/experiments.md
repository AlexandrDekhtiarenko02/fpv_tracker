# Журнал опытов по трекингу

Каждая строка — один проверенный опыт на реальном борту. Смысл журнала в том,
чтобы **не повторять уже отвергнутые гипотезы** и не терять числа.

Правило работы, выведенное на собственных ошибках: **одна правка — один
замер**, предсказание формулируется ДО прогона и записывается в коммит.

| `341031a` | Смаз от выдержки 33 мс → ограничить 8 мс | Усиление упёрлось в потолок, картинка стала вдвое темнее, мелкие дальние цели хуже. Оператор: дело не в выдержке |

## Методологические выводы

**Средний захват мерил не то.** Во всех версиях захваты заканчивались тем, что
оператор отпускал AUX: за все прогоны один уход в HOLD и ни одного LOST.
Метрика отражала ритм тестирования, а не качество. Выводы, сделанные по ней,
пришлось пересмотреть.

**Средний score тоже обманчив.** Он РАСТЁТ, когда трекер уверенно сидит на
неподвижном фоне: фон совпадает с шаблоном идеально. Высокий score не
означает, что рамка на цели.

**Что оказалось честнее:** расхождение матча с предсказанием потока
(`match_flow_gap`) и прямые наблюдения оператора.

**Доля провальных кадров тоже обманывает — и хуже всех.** Она считается
только внутри захвата. Если правка заставляет трекер БРОСАТЬ трудные цели,
эти кадры просто исчезают из знаменателя, и метрика улучшается именно там,
где стало хуже. На `search-window` она показала 23%% → 9%% при пяти реальных
потерях против нуля. **Всегда считать уходы в HOLD рядом с любой метрикой
качества.**

**Проверка на подмену условий.** Прежде чем верить сравнению, надо убедиться,
что оператор водил цель одинаково. Здесь проверено: быстрее всего цель
двигалась как раз в прогоне `main` (4.7 px/кадр, 42%% быстрее 5 px) — и там
ни одной потери. То есть потери на `search-window` не объясняются тем, что
в тех прогонах водили резче.

**Наблюдения оператора били все мои гипотезы.** «Быстрее ведёшь — быстрее
срывается», «объект меньше пятна на фоне — прыгает», «на крупном фактурном
фон перебивает» — каждое указывало на механизм точнее, чем мои рассуждения.

## Замена алгоритма слежения — проверено, пока не нужна

Вопрос оператора: не переписать ли трекер целиком. Замерено, что вообще
доступно на этом железе:

| | |
|---|---|
| KCF, CSRT, MOSSE | **вырезаны** из opencv-contrib 4.13 |
| TrackerMIL | есть, но **3949 мс на кадр** — четыре секунды |
| Nano / Vit / DaSiamRPN | нейросетевые, нужны файлы моделей, на Zero 2W безнадёжны |
| корреляционный фильтр своими руками | **та же цена**, что нынешний матч: 5.9 против 5.6 мс при окне 48, 13.0 против 12.2 при 96 |

Выигрыша в скорости нет. Разница только в природе: наш матч ПОРОЖДАЮЩИЙ
(«найди похожее на сохранённое»), корреляционный фильтр РАЗЛИЧАЮЩИЙ (обучается
отличать цель от окружения, фон входит как отрицательные примеры). Это ближе
к нашей болячке «цепляется за фон», но переписывание не починило бы ни одного
из дефектов, найденных за день: перевёрнутый знак, удвоение вместо гашения,
рассинхрон размера эталона, разомкнутая обратная связь, забытые потолки. Они
бы просто переехали в новый код.

Решение: не переписывать, пока не появится запись кадров, по которой варианты
можно сравнить честно.

## Открытые вопросы

**Коробка не определяет размер цели.** Стоит на значении по умолчанию (8 px в
координатах трекинга) в 76% кадров, максимум за заход 26 px. Для крупного
объекта трекер ведёт случайный участок его текстуры, неотличимый от участка
фактурного фона. Причина измеряется: в лог пишутся `size_est` и `size_skip`
(0 применена, 1 нет матча, 2 score ниже порога, 3 оценка вне диапазона).

**Рамка уползает к краю при сближении.** Шаблон застревает в старом масштабе.
Две попытки лечения были хуже болезни (см. отвергнутое). Остался непроверенный
третий вариант под флагом `TEMPLATE_RESCALE_ON_SIZE_CHANGE`: масштабировать
эталон, снятый при захвате, — он свободен от обеих найденных причин.

## Как воспроизвести замер

```bash
c=$(ls -t ~/fpv_tracker/flight_logs/*.csv | head -1)
grep -m1 -o "commit=[0-9a-f]*" ${c%.csv}.events.log
awk -F, 'NR>1 && $4=="TRACKED" {s+=$10;n++; if($10<0.4)b++} \
  END {printf "score=%.3f плохих=%d%% кадров=%d\n", s/n, 100*b/n, n}' $c
```

## Подбор по записям — первый раз не на глаз

Семь записей со стенда, 2600 кадров, `tools/sweep.py`. Мерило не зависит от
чьего-либо мнения: камера на стенде НЕПОДВИЖНА, значит движется только рука с
целью, и рамка на неподвижном пикселе — это рамка на фоне.

| `DIST_PENALTY` | рамка на фоне |
|---|---|
| 0.55 (было) | 6.1% |
| 0.42 | 3.2% |
| 0.30 | 3.1% |
| **0.20** | **2.6%** |
| 0.12 | 2.6% |

Главный выигрыш там, где оператор и жаловался, — запись `175812`, уход на
перфорированную стену: **17.5% → 1.7%**. Запись `175748`: 6.7% → 0.0%.

Механизм не случаен: предсказание потока САМО сползает на фон, а сильный штраф
заставлял совпадение держаться возле сползшего предсказания.

**Что НЕ помогло** (проверено, чтобы не пробовать снова):

| попытка | итог |
|---|---|
| `MOTION_PENALTY` 0.5 → 0.9 и 1.2 | без изменений |
| `MOTION_REF_DIST` 3.0 → 0.5 | без изменений |
| `MOTION_DIFF_REF` 4.0 → 1.5 | без изменений |
| `MOTION_MIN_SEPARATION` 1.5 → 0.3 | 6.1% → 3.8% **сама по себе**, но с `DIST_PENALTY` 0.20 не складывается |
| `MATCH_WEIGHT` 0.22 → 0.5 | 3.0% — хуже, чем один `DIST_PENALTY` |
| `DIST_PENALTY` вверх (0.75, 0.95) | 6.2% и 11.6% — **резко хуже** |

Защита по движению почти не срабатывала: различимость движения 0.55 при пороге
1.5, то есть цель двигалась медленнее порога.

**Остался нерешённым случай `175804` — 37%.** Рамка уходит на стену к 38-му
кадру и там остаётся. По кадрам видно: цель мелкая и малоконтрастная, а
перфорированная стена — правильный повторяющийся узор. Это тот самый предел
порождающего матча: он ищет похожее, а не отличное от фона.

**Оговорка.** Все семь записей сняты неподвижной камерой при медленном
движении. В полёте камера движется сама, и предсказание потока значит больше.
`DIST_PENALTY` проверять на первом живом заходе.
